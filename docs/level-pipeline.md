# Level authoring pipeline (GMR-39)

## Decision: text-authored JSON and a validator

Status: CURRENT DEFAULT, implementation-tier decision for the owner’s agent-led workflow.
Collision is authored in meters; notebook art follows that geometry. No gameplay verb, rope
rule, simulation timing, or retry behavior changes.

| Option                 | Entity fields / regions                                                     | Agent workflow                                                                       | Cost and trade-off                                                                        |
| ---------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| LDtk                   | Typed fields, entities, world/level regions; JSON export                    | Agents can edit its JSON, but must maintain editor bookkeeping and an export adapter | Best candidate when a human wants a visual editor; adds a second data model today         |
| Tiled                  | Object layers and custom properties; JSON export                            | Editable text, but tile/layer conventions need an adapter                            | Broad map editor; tile-centric structure is unnecessary for meter-based polygon collision |
| Minimal browser editor | Could match our exact collision, paths and camera model                     | Requires building selection, undo, persistence and geometry editing                  | Useful later, but competes with shipping levels; the rope overlay is separately GMR-54    |
| JSON + JSON Schema     | Explicit collision, paths, chamber/checkpoint/camera regions and stable IDs | Direct agent edits, readable diffs, one authoritative source                         | Chosen now; missing a drag-and-drop view, offset by the running game and immediate reload |

The choice is based on the existing three labs and the owner's Claude/Codex resources, not a
claim that text editing is universally better. Revisit LDtk when human spatial editing becomes
a bottleneck. Any editor must export this same validated schema; do not derive collision from art.

Tool capabilities checked against [LDtk entity fields](https://ldtk.io/docs/game-dev/json-overview/entity-fields/)
and [Tiled custom properties](https://doc.mapeditor.org/en/stable/manual/custom-properties/).
The workflow trade-offs above are our assessment for this repository.

## Contract and compatibility

`content/level.schema.json` is the versioned draft-07 JSON Schema. v2 retains v1 geometry and
adds section, telemetry, chambers, checkpoints, camera hints, declared tunnels, required-anchor
take-off tags, and optional hazard visual points. IDs are authored strings, never array indices.
Level telemetry defaults to the level ID; chamber IDs are stable across geometry/name changes.
`migrateLevel` validates and deep-copies v1 to v2 without altering collision or IDs.
`compileLevel` / `parseLevel` compile rect shorthand and tuple/object points to runtime vectors.
Existing v1 labs still load. Unknown versions and fields fail with paths rather than silently
dropping a misspelled gameplay field.

The browser uses a checked-in standalone validator generated by Ajv, not the schema compiler.
After changing the schema, run `npm run levels:compile-schema`; validation and builds check that
the generated file is current. This keeps runtime schema checks within the bundle budget.

Chambers require a stated problem and challenge family. Checkpoints and camera hints are
authoring metadata in this issue; they do not activate respawning or alter the current camera.
Enemies, triggers, mastery routes and one-use anchors remain future feature contracts from doc 32.
GMR-46 adds authored v2 compartment exit angle, speed and alignment acceptance;
see [compartment-exits.md](compartment-exits.md). Other unsupported fields are rejected;
add them with their implementing issue and a migration when needed.

## Author → validate → compile → preview

1. Edit a JSON file in `content/levels`, using `lab-authoring.json` as the v2 example.
2. Run `npm run levels:validate` (also part of `npm run check` and the build prerequisite). Schema errors, invalid geometry,
   tagged required shots, path speed/acceleration, spawn support and exit bounds identify the file
   and offending field. Fix errors before committing.
3. Open `?level=<authored-id>` in the development server. The registry discovers all JSON files,
   rejects duplicate IDs, and selects by ID rather than filename. Unknown IDs give an explicit
   error listing available levels.
4. Save JSON. Vite updates the catalog boundary without reloading the page. The runtime clears
   the old level inside the same physics adapter/world, compiles the new geometry, resets the
   clock/interpolation and input, restores spawn and mover phase, and redraws the scene.
   Invalid edits leave the current attempt intact and report their path; fixing the file retries.

## What validation can establish

The moving-anchor envelope stays at 8 m/s peak speed and 12 m/s² acceleration. Required shots
tagged with `requiredFrom` must fit the current rope impact range and camera envelope, with clear
line of sight. Untagged anchors can be optional or staged later; the validator does not guess.
Hazard silhouettes must fit their collision. Spawn support uses the 0.35 m player radius.
Declared tunnels make intentional passages distinguishable from solid crevices; geometric
warnings prompt review of incidental narrow gaps. Exit checks are geometric bounding checks,
not a proof that a player can complete a route.

Collision policy requires 0.8 m intended passages and 0.1 m walls. The measured 0.72 m clearance is
not a replacement for that safer authoring target. Legacy v1 stress labs intentionally contain
blocked gaps, thin walls and airborne spawns, so authoring-policy violations are emitted as
compatibility warnings while malformed schema, invalid paths and structural geometry remain
errors. New v2 declared tunnels must have 0.8 m clearance. Review warnings explicitly; never
use v1 as a way to evade production validation.

Playtest swing envelopes, resonance, camera framing at bounds, death fairness and route
completion separately. No static validator proves feel or dynamic reachability.
Moving-anchor line of sight is sampled at 17 positions, so tiny blockers between samples still
need review. Thickness measures polygon support-line width; concave local necks need manual
review. Exit feasibility samples a 9×9 grid and may conservatively reject tiny clear pockets.

## Route solver (GMR-101)

Static validation cannot prove a route exists. The route solver does: it plays the level with the
real `Simulation` and `KinematicPhysicsAdapter`, headless, using only Move (digital axis), Jump
(press + release) and Rope (aim at an anchor disc point + press, release later), and keeps the
first route it finds that reaches each goal without dying.

```bash
npm run levels:solve                          # every level in content/levels
npm run levels:solve -- lab-01 lab-moving     # some levels
npm run levels:solve -- <id> --chamber c2     # chambers up to c2 only (no fixture written)
npm run levels:solve -- <id> --chamber c2 --from-checkpoint   # c2 alone, from its checkpoint
npm run levels:solve -- --budget 20000000     # simulated-tick budget per chamber
npm run levels:solve -- --verify              # replay the committed fixtures, no search
```

Output: `content/solutions/<levelId>.json` with, per chamber, `solved`, the plan (steps on
absolute ticks), the solution length in ticks, every input's timing window, the tightest
jump/rope window, search effort and the deaths met while searching, plus an encoded full-level
replay (`encodeReplay`, docs/replay.md) and notes (for example a `requiredFrom` anchor that the
route never needed). `npm run test` replays every committed fixture from a fresh simulation and
fails if one no longer reaches its goals, so a geometry or tuning change that breaks a proven
route is caught in `npm run check`; re-run the solver for that level and review the new numbers.

How it works (`src/tools/route-solver`):

- **Goals.** Chambers are solved in order from the spawn, each continuing from the previous
  chamber's end state, so the fixture is one replay from the spawn. A chamber ends at the first
  checkpoint inside the next chamber (else on entering the next chamber's region); the last
  chamber ends at an accepted exit. A level without chambers is one chamber, `level`, ending at
  the exit. `--from-checkpoint` starts a chamber at rest on its checkpoint for fast authoring
  iteration; that start is not reachable by input, so it writes no fixture.
- **Search.** Best-first search over coarse decisions: set the axis, optionally jump (short or
  full hold), press rope (each anchor in range × 5 impact points on its disc) or release, then hold
  for 4–48 ticks. Order = elapsed ticks + a per-input cost + 2 × 8 ticks/m × free-space distance
  to the goal. States are deduplicated on a quantised key and each 0.5 m cell gets a capped number
  of expansions, so dead ends (hanging on a rope over a pit) cannot absorb the budget. Branches
  that die, or pass within 2 cm of a hazard, are pruned (see the hazard graze finding below).
  Budgets are simulated ticks, so results are deterministic; forks are deep copies used only to
  search, and every reported route is re-run from a fresh simulation at tick 0.
- **Refinement and windows.** Steps the route does not need are dropped, then each jump and rope
  input is moved to the middle of its own window (1-tick refinement of the 4-tick search grid).
  A window is the contiguous range of ticks an input can move, every other input held fixed in
  absolute time, that still reaches the goal (scanned up to ±40 ticks; `capped` marks a window
  at least that wide, `startClipped` one that cannot move earlier because the chamber starts
  there).

Reading windows. A window holds every later input fixed, so it is a lower bound on a player's
leeway (a person re-times later inputs to what they see) and it describes the route found, not
the best possible route; a chamber with an easier route may report a tight window. Proposed
difficulty bands for the tightest jump/rope window of a chamber (PROPOSED, to be calibrated
against playtest death and retry data, not locked):

| Band     | Tightest window | Intended use                                     |
| -------- | --------------- | ------------------------------------------------ |
| Generous | ≥ 12 ticks      | Onboarding, first contact with a mechanic        |
| Standard | 6–11 ticks      | Normal chamber challenge                         |
| Tight    | 3–5 ticks       | Section finales, mastery routes                  |
| Expert   | ≤ 2 ticks       | Optional/expert content only; review if critical |

Current lab results (default budget, one dev machine; `npm run levels:solve`):

| Level          | Result   | Route (ticks) | Tightest jump/rope window                 | Solve time |
| -------------- | -------- | ------------- | ----------------------------------------- | ---------- |
| lab-01         | solved   | 435           | 1 (jump at tick 0, start-clipped; next 6) | 9.6 s      |
| lab-authoring  | solved   | 115           | 29 (single jump)                          | 0.2 s      |
| lab-collision  | unsolved | –             | –                                         | 39 s       |
| lab-exit-miss  | solved   | 101           | 1 (frame-precise braking, by design)      | 0.4 s      |
| lab-exit-shaft | solved   | 59            | – (run only)                              | < 0.1 s    |
| lab-exit-slot  | solved   | 67            | – (run only)                              | < 0.1 s    |
| lab-exit-wide  | solved   | 67            | – (run only)                              | < 0.1 s    |
| lab-moving     | solved   | 755           | 2 (rope release, re-grab sequence)        | 7.9 s      |

`lab-collision` is a collision stress lab: the best state found is at (67.4, 1.7), left of
`conflict-wall`, whose top is about 8 m above `ground-c`. With 40 M ticks the search exhausted
its frontier (about 105 s) without passing it. No intended route is claimed for that lab.

Limits. Digital axis only (analog touch values are not searched). The solver proves that a route
exists; it does not find the easiest route, and it does not judge feel, readability or camera
framing. An unsolved result within budget is a strong hint, not a proof of impossibility.
Findings so far: `lab-authoring` is solved by a plain jump over the teeth, so its tagged required
shot is optional; `lab-exit-miss` (the speed-rejection fixture) can be entered under 2 m/s by
frame-precise braking. The simulation treats a hazard surface within its 1 cm ground probe as
standing ground without a contact, so a player can jump off a lethal floor they never touch; the
solver refuses such routes (2 cm hazard margin) and the issue is reported for a sim fix.
