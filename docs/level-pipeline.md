# Level authoring pipeline (GMR-39)

## Decision: text-authored JSON and a validator

Status: CURRENT DEFAULT, implementation-tier decision for the owner’s agent-led workflow.
Collision is authored in meters; notebook art follows that geometry. No gameplay verb, rope
rule, simulation timing, or retry behavior changes.

| Option                 | Entity fields / regions                                                     | Agent workflow                                                                       | Cost and trade-off                                                                        |
| ---------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| LDtk                   | Typed fields, entities, world/level regions; JSON export                    | Agents can edit its JSON, but must maintain editor bookkeeping and an export adapter | Best candidate when a human wants a visual editor; adds a second data model today         |
| Tiled                  | Object layers and custom properties; JSON export                            | Editable text, but tile/layer conventions need an adapter                            | Broad map editor; tile-centric structure is unnecessary for meter-based polygon collision |
| Minimal browser editor | Could match our exact collision, paths and camera model                     | Requires building selection, undo, persistence and geometry editing                  | Useful later, but competes with shipping levels; the rope overlay is separately GMR-54    |
| JSON + JSON Schema     | Explicit collision, paths, chamber/checkpoint/camera regions and stable IDs | Direct agent edits, readable diffs, one authoritative source                         | Chosen now; missing a drag-and-drop view, offset by the running game and immediate reload |

The choice is based on the existing three labs and the owner's Claude/Codex resources, not a
claim that text editing is universally better. Revisit LDtk when human spatial editing becomes
a bottleneck. Any editor must export this same validated schema; do not derive collision from art.

Tool capabilities checked against [LDtk entity fields](https://ldtk.io/docs/game-dev/json-overview/entity-fields/)
and [Tiled custom properties](https://doc.mapeditor.org/en/stable/manual/custom-properties/).
The workflow trade-offs above are our assessment for this repository.

## Contract and compatibility

`content/level.schema.json` is the versioned draft-07 JSON Schema. v2 retains v1 geometry and
adds section, telemetry, chambers, checkpoints, camera hints, declared tunnels, required-anchor
take-off tags, and optional hazard visual points. IDs are authored strings, never array indices.
Level telemetry defaults to the level ID; chamber IDs are stable across geometry/name changes.
`migrateLevel` validates and deep-copies v1 to v2 without altering collision or IDs.
`compileLevel` / `parseLevel` compile rect shorthand and tuple/object points to runtime vectors.
Existing v1 labs still load. Unknown versions and fields fail with paths rather than silently
dropping a misspelled gameplay field.

The browser uses a checked-in standalone validator generated by Ajv, not the schema compiler.
After changing the schema, run `npm run levels:compile-schema`; validation and builds check that
the generated file is current. This keeps runtime schema checks within the bundle budget.

Chambers require a stated problem and challenge family. Checkpoints and camera hints are
authoring metadata in this issue; they do not activate respawning or alter the current camera.
Enemies, triggers, mastery routes, one-use anchors and exit angle/speed acceptance are future
feature contracts from doc 32, not supported runtime behavior yet. Unsupported fields are
rejected; add them with their implementing issue and a migration when needed.

## Author → validate → compile → preview

1. Edit a JSON file in `content/levels`, using `lab-authoring.json` as the v2 example.
2. Run `npm run levels:validate` (also part of `npm run check` and the build prerequisite). Schema errors, invalid geometry,
   tagged required shots, path speed/acceleration, spawn support and exit bounds identify the file
   and offending field. Fix errors before committing.
3. Open `?level=<authored-id>` in the development server. The registry discovers all JSON files,
   rejects duplicate IDs, and selects by ID rather than filename. Unknown IDs give an explicit
   error listing available levels.
4. Save JSON. Vite updates the catalog boundary without reloading the page. The runtime clears
   the old level inside the same physics adapter/world, compiles the new geometry, resets the
   clock/interpolation and input, restores spawn and mover phase, and redraws the scene.
   Invalid edits leave the current attempt intact and report their path; fixing the file retries.

## What validation can establish

The moving-anchor envelope stays at 8 m/s peak speed and 12 m/s² acceleration. Required shots
tagged with `requiredFrom` must fit the current rope impact range and camera envelope, with clear
line of sight. Untagged anchors can be optional or staged later; the validator does not guess.
Hazard silhouettes must fit their collision. Spawn support uses the 0.35 m player radius.
Declared tunnels make intentional passages distinguishable from solid crevices; geometric
warnings prompt review of incidental narrow gaps. Exit checks are geometric bounding checks,
not a proof that a player can complete a route.

Collision policy requires 0.8 m intended passages and 0.1 m walls. The measured 0.72 m clearance is
not a replacement for that safer authoring target. Legacy v1 stress labs intentionally contain
blocked gaps, thin walls and airborne spawns, so authoring-policy violations are emitted as
compatibility warnings while malformed schema, invalid paths and structural geometry remain
errors. New v2 declared tunnels must have 0.8 m clearance. Review warnings explicitly; never
use v1 as a way to evade production validation.

Playtest swing envelopes, resonance, camera framing at bounds, death fairness and route
completion separately. No static validator proves feel or dynamic reachability.
Moving-anchor line of sight is sampled at 17 positions, so tiny blockers between samples still
need review. Thickness measures polygon support-line width; concave local necks need manual
review. Exit feasibility samples a 9×9 grid and may conservatively reject tiny clear pockets.

## Acceptance and evidence plan

Locked: fixed 60 Hz simulation, persistent physics world, collision-first art, stable IDs,
instant retry, unchanged rope length and release momentum. Open: editor workflow only; no
gameplay question is promoted to locked.

Acceptance: a lab authored in the chosen pipeline loads, validates, hot reloads and resets;
schema and tool choice documented, decision recorded in Linear doc 32. Evidence: migration,
invalid-input and authoring-rule unit tests; repeated runtime replacement without body/joint/
listener growth; real file-edit Playwright reload test; `npm run check`; stacked PR for Claude
review. Human feel and native-device authoring preview remain unverified here.
